# Research: Chronicle load-tier resolution and recap.md

## Decision: player character identified by `role: player`, not a new field

**Decision**: The always-tier query treats an entity as *the* player character when
`type == "character"` and `role == "player"`, per docs/design/22-state.md § "The player's
character".

**Rationale**: This is already the schema's own convention, and `role: player` is already used
throughout `engine/wyrd/creation.py` and the test suite.

**Finding carried into implementation**: `engine/wyrd/entity.py`'s `_ROLES` enum
(`nemesis, ally, companion, bystander, authority, quarry`) does not include `"player"` —
`validate()` currently rejects a real player-character file, and `entity.load`/`load_set` would
raise loading one. This is a pre-existing gap (not introduced by this feature) that blocks the
always-tier query from ever working against real entity files, so it is fixed here as a one-line
addition to `_ROLES` rather than filed as a separate follow-up — the query cannot be correctly
implemented, let alone tested against `load_set`, without it.

**Alternatives considered**: Adding a distinct `is_player: true` flag — rejected, since it would
duplicate what `role: player` already states and the design doc never mentions such a field.

## Decision: companions and threads identified by existing fields, no schema change

**Decision**: With-party companions are `type == "character"`, `role == "companion"`,
`status == "with-party"`. Hot threads are `type == "thread"`, `heat >= 3` (any `status`, per the
issue's literal criterion — see Assumption below). Both already match
docs/design/22-state.md § Companions and § Threads exactly; no new fields needed.

**Assumption**: the acceptance criteria and issue text specify "threads with `heat >= 3`" without
restricting to `status: open`. A thread does not carry `heat` unless it does, so a `resolved` or
`cold` thread that still shows `heat >= 3` (decay not yet applied) is included by this literal
reading. This matches docs/design/28-maintenance.md's separate description of heat *decay* as a
maintenance-time concern, not a filter this query re-applies — a thread's own `heat` field is
the single source of truth this query reads.

## Decision: `chronicle.yaml` and `recap.md` are unconditionally always-tier, not entities

**Decision**: `always_tier()` returns the queried entity subset; callers add `chronicle.yaml` and
`recap.md` themselves (they are two fixed per-chronicle files, not entities in the loadable set —
there is exactly one of each, so there is nothing to query).

**Rationale**: `entity.load_set` operates over entity files only; `chronicle.yaml` is loaded via
`state.load_chronicle` and `recap.md` is plain text, not frontmatter. Folding them into the same
return shape as the entity subset would mean inventing a synthetic "entity" for each, which
neither the schema nor `entity.py`'s existing functions do anywhere else.

## Decision: on-demand fetch reuses `entity.py` directly; no new index

**Decision**: On-demand fetch-by-id is a lookup into the same `entities: dict[str, dict]` mapping
`load_set` already builds keyed by id. On-demand search is a substring/grep-style scan over each
entity's frontmatter values and (optionally) body text, no new persisted index.

**Alternatives considered**: A precomputed search index — rejected as unnecessary for a chronicle
scale (a few hundred files at most, per Scale/Scope in plan.md) and it would itself be exactly the
kind of manifest FR-002 forbids for the always tier; on-demand entities have no equivalent
freshness requirement stated in the spec, but reusing the same "query the live set" pattern avoids
introducing the one kind of staleness this feature exists to eliminate.

## Decision: `recap.md`'s narrative content (where/when, what changed, body/mind sentence) is
caller-supplied text, not generated from raw fields

**Decision**: `generate_recap()` assembles the fixed sections FR-007 requires, but the sections
that require GM judgment or a diegetic (never-raw-numbers) rendering — where and when the
character is, what changed this session, and the one-sentence body/mind read — are accepted as
caller-supplied strings (`where`, `changes`, `body_mind`), not derived by this function from
`taint`/`trauma`/`resolve` or any location field.

**Rationale**:
- No field anywhere in the schema (docs/design/22-state.md, docs/design/25-entities.md) tracks a
  character's current location — "where and when" is GM narrative content
  (docs/design/16-session.md § ORIENT), not stored state, so there is nothing to query.
- docs/design/13-diegesis.md's never-shown list includes thread heat, party tension, bond values
  and character stats — a one-sentence body/mind read generated by mechanically mapping
  `taint`/`trauma` to prose would be exactly this kind of raw-number leak, and any such mapping's
  wording would bake in a register (CLAUDE.md: "tone is a setting property"), which the engine is
  never supposed to do.
- The three hottest threads, `chronicle.yaml`/`recap.md`/who's-present sections *are* pure
  queries over engine state (thread `heat`, `status: with-party`) and are computed directly, per
  FR-001/FR-009 — only the sections above require judgment this layer does not have.

**Alternatives considered**: Generating "where" from the most recently narrated beat's `based_at`
field — rejected; nothing in this feature's scope tracks "most recently narrated beat" as
queryable state, and inventing that tracking is out of scope per the issue (it explicitly scopes
out "the pending/transaction lifecycle" as a later child).

## Decision: `recap.md` write reuses `state.py`'s atomic-write convention

**Decision**: `recap.md` is written via a small addition to `engine/wyrd/state.py` exposing its
existing `_atomic_write_text` helper as `write_text_atomic`, rather than duplicating an atomic
write in the new module.

**Rationale**: `state.py`'s docstring already establishes atomic write as this codebase's
single implementation, shared by `save`/`save_entity`/`save_chronicle`; a fourth call site
duplicating the write-to-temp-then-rename logic would be exactly the kind of drift CLAUDE.md
calls out.
